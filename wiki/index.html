W01 · Context Engineering

Context 與 Grounding

核心概念

模型不應憑自己的記憶猜測場景，而要使用目前任務提供的可靠上下文。RAG 的基本思路是先取得相關資料，再把資料交給模型；但檢索結果相似，不代表內容必然正確或足以回答。

在 RoomQuest 裡

只把主持人確認過的場景資料交給 Planner。未出現在場景 JSON 的物品不能出現在關卡中；照片解析失敗時，可切換到人工輸入，後續流程仍能繼續。

限制

場景 JSON 是封閉世界。程式能確認的是「在已記錄資料中唯一」，不能保證照片之外沒有另一個相似物品。

檢查自己是否理解
  • 敘述能否對回場景資料？
  • 來源是否明確？
  • 是否把檢索相似誤當正確？

W02 · JSON as contract

結構化場景資料

核心概念

自然語言適合給人閱讀，JSON 適合讓程式檢查欄位與條件。場景資料必須具有穩定 ID，才能讓關卡指向某個物品，而不是只留一段難以驗證的文字。

在 RoomQuest 裡

{
  "id": "obj_07",
  "category": "水壺",
  "use": "裝水",
  "color": "紅色",
  "region": "窗邊",
  "dynamic": false
}

關卡另外保存 target_id、constraints 與 answer_source，讓驗證器可以逐欄檢查。

限制

結構化不會自動消除辨識錯誤。時鐘、螢幕和可能移動的物品，仍應標記為會變動，避免作為穩定答案。

檢查自己是否理解
  • 每個物品是否有穩定 ID？
  • 條件能否直接由程式比對？
  • 答案來源是否固定？

W03 · Planning

兩階段規劃

核心概念

課堂的 Two-Stage CoT 先產生多個理由，再挑選內容寫成文章；RoomQuest 將同一模式改成「先規劃關卡結構，再寫玩家看到的線索」。

第一階段選物品、答案來源、順序與依賴
程式先檢查結構錯誤不必等文案寫完才發現
第二階段撰寫故事、線索與分層提示

限制

Planner 仍可能選錯目標，所以只能從 Python 先計算出的候選物品中選擇。

檢查自己是否理解
  • 結構與文案是否分開產生？
  • 關卡是否使用尚未取得的資訊？
  • 答案是否有清楚來源？

W04 · Deterministic checks

Python Verifier

核心概念

AI Model 負責有彈性的生成，Harness 負責限制、工具與停止條件。能明確寫成規則的問題，應交給程式，而不是再請另一個模型猜一次。

六項檢查

存在目標 ID 在場景中
唯一條件只命中一物
順序依賴沒有倒置
安全動作在白名單
穩定答案不會變動
格式JSON schema 合規

限制

規則只能檢查已建模的資料，也不能完全判斷自然語言是否令人誤解，因此仍需要人工出口。

檢查自己是否理解
  • 驗證失敗是否指出欄位與原因？
  • 程式是否擅自替模型補資料？
  • 檢查範圍是否被誠實說明？

W05 · Review and revise

Reflection Loop

核心概念

Reflection 是產生第一版、審查、提供具體建議、再修改。回饋不能只說「不好」，要說清楚哪一個規則失敗，以及模型應修改哪一部分。

AMBIGUOUS_TARGET
obj_03 與 obj_08 都符合
請增加可由場景資料驗證的條件

在 RoomQuest 裡

AI 只重寫未通過的關卡，修改後重新驗證。最多兩次；若仍不通過，就停止自動迴圈，交給主持人處理。

限制

Reflection 不代表一定會修對。原始規格與程式檢查優先，修改後不能跳過驗證。

檢查自己是否理解
  • 回饋是否具體到可以修改？
  • 是否只重寫失敗部分？
  • 是否有重試上限？

W06 · Traceability

人工核准與可追溯性

核心概念

可靠流程不只保存結果，也保存來源、轉換方式與檢查紀錄。RAG 教材將正文、metadata、索引對照與設定分開保存，讓結果能追溯與重現。

在 RoomQuest 裡

主持人預覽場景 JSON、關卡結構、驗證報告和修改紀錄，再決定核准、手動修改或重新生成。玩家只取得核准後的遊戲，遊玩中不臨時呼叫 AI。

限制

人工核准增加操作成本，但能處理照片漏拍、現場變動和語意歧義。MVP 的目標是降低人工負擔，而不是假裝完全自動。

檢查自己是否理解
  • 能否由投影片回到 Wiki 與來源？
  • 是否保存失敗原因與修改次數？
  • 未完成能力是否清楚標示？
