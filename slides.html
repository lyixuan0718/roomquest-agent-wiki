ROOMQUEST · 01

一張照片，真的能變成解謎遊戲嗎？

答案不是「請 AI 隨便出題」，而是先把真實場景變成能被查驗的資料，再讓生成與驗證輪流工作。

W01 Context 與 GroundingS01

問題 · 02

直接叫 AI 出題，會發生什麼？

憑空出現線索引用照片裡不存在的物品。
條件不唯一「窗邊的紅色東西」可能同時指水壺與書包。
答案會改變時鐘、螢幕或可移動物品讓答案失效。

這些不是文案問題，而是流程沒有提供限制與檢查。

核心觀念 · 03

Agent 不只是一個模型

AI Agent = AI Model + Harness
AI Model理解照片、規劃關卡、撰寫線索與提示。
Harness提供資料、限制動作、呼叫工具、驗證輸出、決定何時停止。

GROUNDING · 04

先把照片變成場景資料

自然語言很靈活；JSON 讓每個物品有 ID，也讓顏色、用途、區域與是否會變動都能被程式讀取。

{
  "id": "obj_07",
  "category": "水壺",
  "use": "裝水",
  "color": "紅色",
  "region": "窗邊",
  "dynamic": false
}

規則：不在場景 JSON 裡的物品，不能被拿來出題。

W01W02S01S02

PLANNING · 05

先規劃，再寫線索

第一階段決定目標物品、答案來源、順序與依賴。
結構檢查先確認計畫可用，不急著寫漂亮文案。
第二階段撰寫故事、正式線索與分層提示。

分開做的好處：即使文案很漂亮，也不能掩蓋一條根本無法完成的關卡。

TOOL USE · 06

能用規則確認的，交給程式

存在物品 ID 確實存在
唯一條件只命中一物
順序關卡依賴沒有倒置
安全動作在允許清單
穩定答案不會隨時間改變
格式JSON 欄位符合規格

REFLECTION · 07

失敗不是重來，而是帶著原因修改

錯誤：AMBIGUOUS_TARGET
obj_03 與 obj_08 都符合

要求：增加可驗證條件
範圍：只改第 2 關
第一次「找到窗邊的紅色東西。」
修改後「找到窗邊可以裝水的紅色物品。」

最多修改兩次；仍不通過就停止，交給主持人。

W05 Reflection LoopS02S04

GRAPH · 08

RoomQuest 的完整 graph

① 取得與確認照片 → 場景 JSON → 主持人修正
② 規劃與生成候選物品 → 關卡鏈 → 線索提示
③ 驗證與核准程式檢查 ⇄ 指定關卡重寫 → 人工核准
核准的 game.json → 玩家遊玩（不再呼叫 AI）

CASE · 09

「紅色物品」為什麼不夠？

條件 A窗邊 + 紅色

符合：紅色水壺、紅色書包
結果：2 個，不通過
條件 B窗邊 + 紅色 + 可以裝水

符合：紅色水壺
結果：1 個，通過

唯一性不是請 AI 說「看起來沒問題」，而是用全部場景物品實際篩選。

LIMITS · 10

可驗證生成，不等於保證正確

可以攔下不存在、資料內不唯一、答案會變動、危險動作。
仍可能漏掉照片外物品、現場移動、玩家對文字的不同理解。
所以保留來源追蹤、重試上限、主持人核准與人工備案。

RoomQuest 的重點：讓創意交給 AI，讓可以確認的部分留下證據。
