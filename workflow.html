Loop / Graph 與實際執行

這個流程把最容易出錯的「資料整理」檢查提前，並在 Wiki 與投影片之間增加可追溯性檢查。

先討論、後生成

Wiki 不是一開始就直接產生

先決定為什麼選這些資料、知識要怎麼拆，以及哪些內容不放進主線。

討論前的候選

最初曾比較 RoomQuest 與斷捨離助手，也列出照片解析、Harness、Embedding 模擬玩家等 8 個候選條目。

討論後的收斂

選擇能直接支撐課程主線的 6 份資料與 6 個 Wiki 條目；未實作或需要額外實驗的內容移到延伸，不寫成現有能力。

取得、整理、檢查、生成

綠色節點是程式或人工檢查。未通過時，只退回前一個負責的節點，不從頭全部重做。

1. Discuss比較題目、選擇資料、拆分與合併知識條目
2. Ingest讀取 3 份 PDF 與 3 份 notebook
3. Normalize擷取正文、標題、metadata 與來源 ID
4. Source Check內容是否可讀、可追溯且與主題相關？
5. Build Wiki合併重複概念，形成六個知識單元
6. Retrieve依教學問題挑選相關 Wiki 條目
7. Outline安排問題、概念、案例、限制的順序
8. Trace Check每張投影片能否回到 Wiki 與來源？
9. HTML Slides產生、檢查、修正教學簡報

Loop A：來源不合格

Source Check 不通過 → 回到 Normalize，調整擷取規則或改讀 notebook 的 code cells → 再檢查。目的：不要等簡報寫完才發現資料根本不能用。

Loop B：投影片無法追溯

Trace Check 不通過 → 先回到 Outline 補 Wiki 對應；若 Wiki 缺概念，再回到 Build Wiki。目的：避免 AI 用常識補出來源中沒有的內容。

Reflection

哪個節點最常出錯？

1

最常出錯：Normalize

PDF 的版面會造成斷字；notebook 的說明與執行邏輯分散在 markdown 與 code cells。若直接摘要，很容易漏掉真正的流程。

2

檢查往前移

原本想在投影片完成後才看來源，後來改成每一份資料在進入 Wiki 前，就檢查標題、正文、來源 ID 與可用概念。

3

Workflow 的修改

新增 Source Check 與 Trace Check 兩個節點。前者避免垃圾資料進 Wiki；後者避免投影片離開 Wiki 自行發揮。

為什麼這樣設計？

錯誤越晚發現，重做範圍越大。把來源檢查移到 Wiki 生成前，可以只重做擷取；把追溯檢查放在 HTML 生成前，可以只修改大綱或缺少的條目。兩個 loop 都有明確返回點，不會無限重生整份成果。
